# CarDash V3 beta 5 — validation

## Beta 5 candidate — release held for the navigation issue

Beta 5 replaces independent-axis stretching with a native display request based on the browser viewport's aspect ratio. The source is capped at 1,280 pixels wide, 960 pixels high and 921,600 total pixels, and remains at least as wide as tall in narrow previews. The browser preserves source proportions; iOS selects the app layout for the negotiated display. A four-column, three-row grid is not guaranteed. Viewport changes use a generation-checked native-session restart with the existing audio choice retained.

The release retains the H.264/MediaSource video renderer. No vehicle-restriction bypass is included, and no Tesla Drive test has validated this release. Phone / Bluetooth remains the default, with Browser audio optional. After the beta 4 changes, the user reported successful audio over actual Tesla Bluetooth; that report does not establish steering-wheel controls or navigation prompts mixed with music.

The MSE resizing candidate passed 98 Python tests, 54 JavaScript tests and one cross-process launcher test (153 total). New regressions cover coherent native display/HID/MP4 sizing, independently encoded cropped H.264 SPS, stale-session resize rejection, aspect-preserving touch mapping, request/body timeouts, and recovery from overlapping status/resize operations.

On the supported physical iPhone, a fresh 773×601 browser session negotiated and decoded 1088×846 native video. Reviewed screenshots showed an unstretched five-column, three-row native Home grid, Waze and YouTube Music. Controlled viewport changes verified 773×499 → 1194×770, 773×601 → 1088×846, 1600×900 → 1280×720, then restoration to 1088×846, with no browser video errors. An earlier matrix attempt was discarded because another viewer changed the native geometry and the test harness used an outdated toolbar-height assumption.

A 92.06-second continuously locked trial selected Waze, YouTube Music and Home through native input, then restarted at the controls-visible resolution and returned to full-screen resolution while still locked. Both screen-off and awake Lock Screen states were observed. Native display verification and browser playback recovered after both deliberate resizes with no browser video errors. Reviewed screenshots verified the selected interfaces. Playback remained paused; this was not a new music-quality or Bluetooth test.

All 35 installed candidate payload hashes matched the package manifest. Preservation checks matched 585 original project entries, the original DEB, 203 outer-project files and 23 original installed files/preferences. The candidate is not published: the user’s report that the whole navigation display freezes in Tesla Drive remains a release blocker. The successful desktop/phone tests do not resolve or validate that vehicle behavior. The historical results below retain their original scope and are not beta 5 acceptance evidence.

## Historical beta 4 validation

Target: iPhone 8 Plus (`iPhone10,2`), iOS 16.6 build 20G75, Dopamine rootless. Beta 4 uses the real phone with a Mac Chrome viewer forwarded over USB; inherited beta 3 Wi-Fi/USB-free evidence is recorded separately below. No new Tesla driving test was performed on the computer.

## Changes and regressions

- The native 1280×720 source now fills the browser rectangle by stretching both axes. Input coordinates use the same rectangle. This fills the available web viewport but does not change the native resolution or Tesla system chrome. Proportions can change.
- Phone / Bluetooth is the initial default and the output selection persists in V3’s own settings file. Browser audio is optional. A short-lived PID-bound lease scopes the exact-build MediaExperience routing adapter to an owned CarDash session. It retains valid native audio/authentication declarations, avoids opening a browser audio connection in phone mode, and restores native routing intent on stop or lease expiry. Real Bluetooth selection and steering-wheel controls still require a parked car trial.
- Device research found Python 3.9’s Darwin monotonic clock uses a per-process origin despite reporting `mach_absolute_time()` as its implementation. Cross-process leases now use raw Mach ticks and their timebase. Earlier experiments with invalid leases were not counted as routing passes.
- Native audio hook initialization was corrected to avoid notification reads while holding its routing mutex, and the monitor starts after synchronous dyld registration. VM guards traverse shared-cache submaps to verify actual leaf permissions. Exact firmware UUID and instruction checks remain enforced.
- The old two-second `forceKeyFrame` timer repeatedly tore down and rebuilt iOS’s video encoder. In the recorded failure, 34 restarts produced only 33 resumes; the final teardown stalled, native commands returned 408, and the encoder later reported a driver-stop counter mismatch. The two-second timer is removed. A joining viewer still requests its initial keyframe; long GOP recovery is limited to one request per 30 seconds when no IDR arrives for 30 seconds or compressed GOP data exceeds 8 MiB. The failed run is not an endurance pass.
- Removing frequent encoder resets exposed a second bug: arbitrary SourceBuffer trimming could delete the current long GOP through the next random-access point. The browser now trims only before an emitted IDR at least three seconds behind the playhead, using exact 90 kHz clock timestamps; the server retains at most 32 such markers. If there is no safe trim point and retained video exceeds 90 seconds, the browser reports an error and reconnects instead of retaining an unbounded history. The separate 4 MiB pending-read queue bound remains.
- The previous car-session logs showed browser heartbeat timeouts and five audio-queue saturation events, but had no gear state or browser playback/viewport counters. They do not establish why playback stopped when shifting into Drive. Beta 4 adds bounded playback counters, visibility/pause state and decoder errors for diagnosis. **No Tesla driving-video restriction bypass is included.**
- HTTP error cleanup now handles Python 3.9’s separate asyncio.TimeoutError type. Audio-output changes disable/guard Start and Stop until the stop/configure/start sequence finishes, avoiding conflicting sessions.

## Local verification

89 Python tests, 43 JavaScript tests and one cross-process launcher test pass (133 total). Regressions cover wide/tall coordinate mapping, default/persisted audio choice, asynchronous output-switch races, raw Mach lease clocks, stop/start cleanup, firmware/memory guards, concurrent native callbacks, lease expiry and restoration, metric bounds, timeout cleanup, and retaining viewer-join keyframes with bounded long-GOP recovery instead of two-second encoder resets. Builds use arm64/iOS16.6 warnings-as-errors and package-path/credential audits.

## Beta 4 physical-device results

The final runtime candidate was installed and its 34 payload hashes matched the build manifest. Testing used a private Mac Chrome viewer over USB forwarding; it did not replace the user's normal browser profile.

- A **94.80-second continuously locked trial** switched YouTube Music → Waze → Dashboard → YouTube Music with the iPhone speaker playing throughout. Reviewed screenshots confirmed each interface. The browser decoded 2,807 additional frames with no new video error or connection. Separate visible pause/resume controls changed independent MediaRemote playing state `1 → 0 → 1` while lock state remained locked and output remained Speaker.
- Phone / Bluetooth → Browser audio → Phone / Bluetooth was exercised on the final runtime. Speaker output changed to CarAudio for browser streaming, then returned to Speaker. Browser audio produced 936,870 decoded sample frames and nonzero analyser output, with no sequence gaps or dropped sample frames; one startup underrun was recorded. Returning to phone mode closed the browser audio connection. The user independently confirmed clear music from the iPhone speaker. This verifies speaker output, not actual Tesla Bluetooth or steering-wheel controls.
- The final session reached **395 seconds (6 minutes 35 seconds)** and 11,605 browser-decoded frames. A 349.53-second sampled interval remained continuously locked with Speaker selected and gained 10,463 decoded frames, with no additional video errors, reconnections or dropped video frames. Eleven GOP-aware buffer trims completed; a late MSE checkpoint had ready state 4, an approximately 14-second retained range and no queued bytes. The nine cumulative browser video drops occurred before this measured interval. This short desktop trial does not establish long-drive reliability.
- Closing the browser without Stop ended the native session after **13.92 seconds**. Playback was paused first. The session audio request/lease cleared to zero and the native routing override cleared; the output remained Speaker. A fresh viewer then authenticated, activated and decoded 109 frames at its 13-second checkpoint while the phone remained locked. Phone output was remembered and no browser audio connection opened. The fresh session was explicitly stopped.
- Live viewport checks at 1280×720, 900×950 and 1920×800 filled the entire available video width and the height below the 55-pixel toolbar. Full-screen mode filled 1920×800 at position 0,0; touch coordinates continued to match the stretched display. This does not increase the native 1280×720 rendering resolution.

Host preservation matched all 585 original-project entries and the original DEB; all 203 outer update-product source hashes and 23 original installed payload/preference hashes also matched their baselines. Final package provenance and byte-reproducible source-archive assembly are checked before publishing.

## Historical beta 3 validation

Test device: iPhone 8 Plus (`iPhone10,2`), iOS 16.6 build 20G75, Dopamine rootless. The receiver runs on the phone. Beta 3 trials use a Mac browser over home Wi-Fi with USB disconnected; the Mac does not receive/decrypt the native protocol or host the native session.

## Beta 3 USB-free investigation and results

Beta 2 accepted the CarKit request without starting video when USB was absent. Device logs showed the simulator transport selecting `[::1%en2]:62000`; removing `en2` released its session host. Four alternative host/address profiles also failed to start without USB. This was a native transport dependency, separate from the Tesla address issue.

REA analysis of the phone's actual APTransport implementation identified the network-state and interface-change paths. The beta 3 adapter applies only to the exact supported image UUID and checked function prologues, and only to CarDash V3's matching host, port and loopback address. It supplies `lo0` to that request and preserves its host during physical USB changes. Original network-state inputs are restored after the native call; other hosts follow the original functions. No Apple firmware binary is shipped or changed on disk.

- The prototype continued after USB removal: at the recorded checkpoint it remained authenticated and activated, with 2,527 native frames at 93 seconds. After an explicit stop, a fresh session started with USB still disconnected and produced 354 native frames in 17 seconds.
- The installed beta 3 package then started a fresh USB-free session over Wi-Fi with authenticated H.264 video, browser HID input and YouTube Music playback. Native audio negotiated 44.1 kHz stereo PCM; browser decoding and nonzero audio analyser output were observed. These are home-Wi-Fi measurements, not a Tesla acceptance test.
- A controlled **66.82-second continuously locked, USB-free trial passed**. Native input selected YouTube Music, paused/resumed playback, selected Waze, opened Dashboard with Home, returned to YouTube Music and paused at the end. Reviewed screenshots confirmed Waze, Dashboard, YouTube Music and its paused control state. Independent MediaRemote observations reported playing `1 → 0 → 1 → 0` on the CarAudio route. The display remained off and lock state remained locked throughout the measured trial. The browser gained 1,872 decoded frames with no new video error or reconnection. It received another 2,718,210 audio sample frames, with no sequence gaps; one scheduling drop and two underruns occurred across the deliberate pause/resume sequence. These measurements do not establish glitch-free long-drive playback.
- A fresh native session then started **while the phone remained locked**, with the Lock Screen awake. In 8.26 seconds the checkpoint showed authentication/activation, 102 native frames and 53 browser-decoded frames. An old-session touch was rejected, and final cancellation reported no native session remaining. Playback was paused before cleanup.
- The first roughly 105-second beta 3 lock run established stream/audio continuity only: its intended app switches did not succeed, so it is not an app-switching pass. After a userspace restart, switching worked with the preexisting CarPlay On-Screen package still enabled. Additional manual browser clicks overlapped a later Home-button test and made that attempt unsuitable for acceptance. The controlled 66.82-second result above is the app-switching acceptance evidence. No CarPlay On-Screen disable/removal was performed, and this investigation does not establish it as the cause of the earlier failure.
- A separate boot issue left the service stalled at the `xpcproxy`/Python launch boundary. The native wrapper and scoped tweak isolation alone did not fix it: the Adaptive launchd configuration again failed to reach its entry point during a fresh userspace boot. Rebootstrapping restored service, and both Adaptive and Interactive variants passed warm starts; those warm tests were not used as boot acceptance.
- The final `ProcessType=Interactive` configuration **passed an actual userspace-reboot trial**. A newly created service process executed and initialized, and IPC, the native adapter and the verified Tesla address were ready 5.50 seconds after the recorder first observed that new process. This is not the total reboot duration. The user unlocked the phone but confirmed that CarDash V3 remained closed; no manual app launch or service rebootstrap was needed. This is an observed startup correction on the supported device, not a guarantee for every boot or jailbreak environment. Scoped `DISABLE_TWEAKS=1` remains limited to the V3 daemon/helper, with fixed startup-stage diagnostics retained. No CarPlay On-Screen or other package was disabled or removed for this trial.
- After the successful reboot, a fresh browser authenticated, activated, decoded live native video and opened the native Home grid while the companion app remained closed.
- The packaged network bridge verifies `100.99.10.2` on `lo0` before displaying the Tesla URL. That address previously opened the page in the user's Tesla; native beta 3 playback still needs vehicle confirmation.

The current adapter retains the native helper object across interface-event restoration, including when the callback releases its final native reference. Session cleanup checks the generation again under the lifecycle lock, preventing a delayed old connection from ending a replacement session. Native input-response diagnostics distinguish receipt of a command from a visually verified app change; neither successful transport status nor an accepted input response alone counts as switching acceptance.

## Historical beta 2 physical-device results

The following results were obtained with USB connected. They remain regression evidence, but do not by themselves establish USB-free behavior for beta 3.

- Native authentication, activation, H.264 video, HID input and actual music audio work together. Audio negotiated `type100/media`, 44.1 kHz stereo PCM, with nonzero decoded samples and no authenticated-packet rejects in the measured trials. The browser AudioContext ran and produced nonzero analyser output. The user independently confirmed clear music from the Mac speakers.
- After removing V2/Canary, CarPlay Diagnostics and CarPlay Loopback, restarting the affected processes and respringing, a **105.68-second continuously locked trial passed**. Immortalizer's injection files were temporarily isolated for this test. Waze → YouTube Music → pause → resume → Waze → YouTube Music all worked through native input. Screenshots confirmed the app and control changes; independent MediaRemote observations confirmed playing=1, then 0, then 1 on the CarAudio route. The browser finished with 4,086 decoded frames, one video connection, zero video errors and one audio connection. It recorded no audio sequence gaps, one scheduling drop and three underruns across the deliberate pause/resume sequence.
- A separate wake test observed the display turn on while lock state remained locked, then verified another 30.09 seconds of continuous audio/video. It ended with 5,424 decoded frames, one video connection, no video errors and no audio sequence gaps.
- The final corrected session reached **420 seconds (seven minutes)** with 11,841 decoded browser frames, one video connection, zero video errors and one audio connection. Browser audio processed 17,038,230 sample frames, with no sequence gaps. Its one scheduling drop and three underruns came from the earlier deliberate pause/resume sequence; neither count grew during continued playback. The phone remained locked through the final endurance observation.
- A prior 106.11-second locked trial also passed before old test-hook removal. That result alone was not used to claim independence from those hooks.
- Closing the browser without pressing Stop ended the native session in 16.46 seconds, including cancellation. A fresh browser then authenticated and activated a new native session, displayed YouTube Music and played audio while the phone remained locked. The old session's input was rejected. Separate stale-session video/audio/touch/stop/heartbeat requests also returned errors without disrupting the active session. Playback was explicitly paused before cleanup.
- Independent synthetic AAC-LC 44.1/48 kHz stereo vectors decoded on the physical phone to 12,288/13,312 frames, RMS 1933.26/1930.58 respectively. Native AAC negotiation has not been observed; actual music trials used PCM.
- The kernel readback confirmed the receiver's own active/inactive memory limits at 128 MB. This is a configured limit, not a measured guarantee of long-term memory use.

## Retained beta 2 fixes

The five-minute product deadline is removed. Browser-disconnect cleanup, parent-death/EOF handling, a renewable native-process lease and bounded queues remain. Sessions are not kept alive after an abandoned browser indefinitely.

The original audio failure was iOS rejecting the incomplete duplex format table with `APCarPlayAudioFormatsCreate kParamErr(-6705)` for 100/telephony. Supplying the required 16/24 kHz mono input declarations enabled media audio. No microphone capture is implemented; requested input transport sends authenticated silence and is explicitly labelled unsupported for voice input.

An earlier endurance run reached 409 seconds without a video error but later exposed an asynchronous SourceBuffer trim race. The busy-buffer guard now has a regression test. Clean-runtime testing then exposed a buffered-native-frame burst overflowing a healthy HTTP viewer queue. The parser now processes bounded batches and lets the writer drain. A 220-frame encrypted burst regression fails against the prior implementation and passes with the correction. These earlier failed runs are not presented as final acceptance passes.

Audio overflow discards oldest records within a 64-record/256 KiB bound, preserving per-lane reset markers. It does not force a reconnect for a transient burst. Blocked network writers still time out. Browser scheduling is bounded to 0.5 seconds. Reconnect tests cover quiet EOF, failed headers, stale generations, old callbacks and queued touches. Real-device browser Mute/Unmute checks preserve the native session.

## Remaining vehicle and compatibility checks

Beta 5's native viewport sizing and Tesla video/input behavior, Personal Hotspot interruption/recovery, navigation voice prompts mixed with music, steering-wheel controls, and long-duration thermal/battery behavior require vehicle testing. USB-free startup and streaming have been exercised over home Wi-Fi, and the user separately reported successful Tesla Bluetooth audio after beta 4. Those results do not establish the remaining checks. Beta 5 adapts native source dimensions within a 1,280-pixel width, 960-pixel height and 921,600-pixel total budget; iOS determines the resulting app grid. The earlier fixed-resolution and stretched-display trials above remain historical beta 4 evidence. Microphone/Siri/call input is unsupported. Other phone models/iOS builds are unverified and rejected by the installer.

CarBridge and Immortalizer were preexisting third-party packages. Full-app interfaces shown during these trials use CarBridge; this release does not replace or bundle it. Results without CarBridge must not be inferred. The historical beta 2 clean locked trial ran without Immortalizer injection; its files were restored afterward. Do not infer that the beta 4 trial repeated that isolation. YouTube Music's installed old version shows an unsupported-version message, while its existing Now Playing playback remains usable on this device.

## Release artifacts

The downloadable DEB is built from the tagged source commit. Its manifest records that commit and hashes every payload file. The matching source archive includes `SOURCE-COMMIT.txt`; rebuilding that archive on the documented toolchain produces the identical DEB. Release assembly verifies that executable/backend/web and launchd payload hashes match the physical-device candidate; documentation and provenance updates are recorded separately. The published checksum file names the actual GitHub assets. Private evidence, device caches and identity material are excluded.
